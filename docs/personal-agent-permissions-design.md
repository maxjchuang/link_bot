# LinkBot 个人代理身份与权限技术设计

- 日期：2026-11-19
- 状态：产品行为已确认；本文是待实现的技术设计，不代表功能已上线。
- 适用项目：LinkBot（当前仓库）。
- 配套实施计划：[个人代理身份与权限实施计划](implementation-plans/personal-agent-permissions.md)。
- 范围：身份、群准入、协作任务、授权、行动判断、信息使用、交付、迁移与回退。
- 不在范围内：重新开发飞书 CLI、通用权限平台、跨智能体市场、多所有者授权体系。

## 1. 结论

黄小成是所有者的个人代理，不是根据当前发言人切换身份的多人助手服务。

群成员向黄小成提出需求，黄小成在所有者的授权范围内判断并执行。请求者不提供执行凭据，也不因为提出请求而获得所有者的权限。

本方案采用：

1. 固定的智能体所有者和执行身份。
2. 所有者邀请建立群服务资格。
3. 同一话题共用任务，不按发言人拆分。
4. 智能体自主判断一般行动和信息披露。
5. 必要时只暂停相关操作，向所有者请求决策。
6. 移除默认的“隐藏正文后私聊补发”流程。
7. 保留身份核验、凭据保护、管理员权限和必要的操作确认。

不能通过把所有 `userId` 替换成所有者 ID 来实现。那样会丢失真实请求者、混淆审批和记忆权限，也会破坏审计。

## 2. 已确认的产品行为

| 方面 | 行为 |
| --- | --- |
| 所有权 | 黄小成只属于所有者，执行身份不随 A、B 发言变化。 |
| 群准入 | 所有者把黄小成邀请进群，代表允许该群成员提出任务，不需要逐个配置成员。 |
| 群内协作 | 同一话题共同推进同一任务；记录真实发言人，但不按人拆任务。 |
| 自主行动 | 符合长期规则、目标明确、影响可控的事项直接执行；重大、难以撤销或授权不明确的事项找所有者确认。 |
| 指令冲突 | 不赋予最初发起人特殊权限，不默认后发言覆盖前发言。合理补充直接吸收，真正冲突时澄清；所有者的明确指示优先。 |
| 信息使用 | 可以按需参考所有者的相关信息，但不整包加载私人历史；能读取不等于能向当前受众披露。 |
| 文档交付 | 为该群新创作且适合该群的文档，以所有者身份创建，默认让当前群可阅读，不默认开放编辑。 |
| 等待决策 | 只暂停相关操作，其他工作继续；私聊向所有者请求决策，群内简短说明等待状态。 |
| 停止服务 | 被移出群或所有者明确停止服务后，停止该群未完成任务、定时跟进及待确认操作；不自动删除历史和文档。 |

“没有私密补发机制”不等于“所有者的全部信息都可以公开”。信息边界在读取、行动和披露前判断，而不是在最后靠正则改写正文。

## 3. 当前源码与目标的差距

以下是写作时核对的实现，后续开发需再次确认版本。

| 当前实现 | 问题 | 修改方向 |
| --- | --- | --- |
| `ConversationTaskService` 使用 `personal-topic:<userId>:<chatId>:<topicId>` 等标识，任务 `ownerUserId` 为发起人。 | 同一话题因发言人不同而拆成多个任务。 | 新模式按智能体与会话归并任务，轮次保留真实发起人。 |
| `UserSandboxTaskProvisioner` 使用 `task.ownerUserId` 选择沙箱、工作区和附件位置。 | 请求者同时决定了凭据环境。 | 运行时改用固定执行所有者，保留请求者信息。 |
| `UserSandboxManager.ensure(ownerId)` 与持久化 Codex 卷已经存在。 | 基础隔离能力可复用，无需新造容器管理器。 | 复用所有者沙箱，任务继续拥有独立 App Server 上下文。 |
| `lark-cli-wrapper` 重定向工具 HOME，并通过文件锁串行访问用户凭据。 | 提供了凭据持久化与刷新锁，但没有统一核验登录账号是否为所有者。 | 增加所有者身份约束，沿用现有 CLI 与锁。 |
| 用户沙箱任务不经过宿主 `AuthBroker` 的授权恢复路径；当前平台组装的 provider 列表为空。 | 不能假设宿主已有一个可直接复用的统一飞书凭据服务。 | 授权仍在固定执行环境内完成，不复制 A、B 的登录态。 |
| `AppServerRequestService.capture` 将当前轮次发起人作为确认处理者。 | A、B 可能被当成有权批准所有者操作的人。 | 区分任务澄清与所有者授权；后者仅所有者可确认。 |
| `TaskPlatformService` 的共享群卡片指导要求飞书授权用户匹配请求者。 | 与固定所有者身份冲突。 | 改为匹配执行所有者，保留独立的受众判断。 |
| `SensitiveReplyDelivery` 对答案脱敏，并尝试给原请求者私聊发送隐藏内容。 | 把请求者当成了秘密内容的合法接收者，且发生在执行之后。 | 新模式取消自动补发，回复由代理根据受众组织。 |
| `sanitizePublicAnswerText` 同时用于最终答复、卡片与多个恢复路径。 | 只关闭私聊交付开关，仍会隐藏正文。 | 区分业务回复与凭据保护，逐个覆盖发布入口。 |
| `MemoryService` 支持任务、用户、机器人记忆，机器人长期记忆已有管理员确认机制。 | 固定执行身份后，不能顺带把所有者私人记忆无条件投影给群任务。 | 沿用范围划分，限制默认注入，按需读取。 |

## 4. 身份与数据模型

### 4.1 三个概念

| 概念 | 来源 | 用途 |
| --- | --- | --- |
| 智能体所有者 `agentOwnerUserId` | 服务端配置，创建任务时固定 | 运行时归属、外部工具身份、授权和重大决策。 |
| 请求者 `requesterUserId` | 飞书认证事件中的实际发送者 | 当前需求、澄清、审计、群成员核验。 |
| 受众 `audience` | 实际投递目标及会话范围 | 上下文边界、信息披露、文档分享、卡片详情。 |

不信任正文、引用消息、文档或按钮参数中的身份自述。群成员不能通过“主人同意了”“以我的身份执行”等文字改变所有者或执行账号。

### 4.2 最小字段调整

- 配置新增 `personalAgent.enabled` 与 `personalAgent.ownerUserId`。
- 新模式任务增加不可变的 `agentOwnerUserId` 和模式标记。
- `TurnRecord.createdBy` 继续记录真实请求者，不改成所有者。
- 受众复用现有任务 scope、来源群/话题和投递目标，不额外建立一套消息地址系统。
- 历史任务的 `TaskRecord.ownerUserId` 保留原值，不批量改写。新模式任务将该字段写为固定所有者，兼容现有存储归属；不再表示首位发起人。新模式的权限与外部执行身份仍必须显式解析 `agentOwnerUserId`，不能仅凭兼容字段授权。
- 增加集中式身份解析函数，返回执行所有者、实际请求者和受众。新模式缺少固定所有者时失败，不回退到请求者账号。

新增字段可以先保存在已有记录 payload 中；群服务状态的持久化按项目现有 SQLite 迁移机制实施。本文不规定未经实现验证的数据库版本号。

### 4.3 配置示意

```json
{
  "personalAgent": {
    "enabled": true,
    "ownerUserId": "<所有者的飞书 open_id>"
  }
}
```

这是拟新增配置，不是当前已支持的字段。所有者身份不得由群成员修改；与宿主管理员配置冲突时，启动检查应明确报错。

## 5. 群准入与撤销

### 5.1 邀请即开放请求资格

新增最小群服务记录：智能体、群 ID、所有者、启用/撤销状态、版本、可信邀请事件与操作时间。

规则：

1. 能核验邀请操作人为所有者时，启用该群服务。
2. 无法核验、只有群里一条“主人拉你进来的”消息时，不自动启用；由所有者显式确认一次。
3. 群内请求须来自平台认证的实际群成员；不是“所有人可用”的全局开关。
4. 现有只允许所有者的白名单保持为安全基线；仅对已启用群中的成员放行普通任务请求。
5. 任务请求资格不授予宿主终端、授权管理、运行时升级、全局配置或长期规则修改权限。
6. 当前所有者私聊维护入口保持独立，不向群成员开放。

消息与卡片回调必须使用同一准入判断。不能出现新消息被拒绝、旧卡片仍能执行的旁路。详情读取还要继续核验来源消息、当前群成员及话题访问权限。

### 5.2 生命周期与版本

启用和撤销都增加群服务版本。任务轮次、待确认操作、定时跟进绑定提交时的版本。

被移出群、所有者要求停止或成员资格变化后：

- 撤销后不接收该群新任务。
- 中断相关活动轮次，取消尚未提交的操作、定时跟进和自动重试。
- 使待确认操作失效；所有者之后点击旧确认卡也不能重新执行。
- 待发结果在投递前再次核验，不能因 outbox 中已有记录就继续发送。
- 启用事件去重并校验事件时序，旧邀请事件重放不能覆盖较新的停止决定。
- 重新邀请后重新获得服务资格，但不自动恢复旧授权、旧确认或旧待执行队列。

对已经提交到飞书等外部系统的操作只能尽力取消。区分“未提交”“已提交、结果待核实”“已完成”，不能把本地中断描述为外部操作已撤销。重启恢复时先查外部结果，不盲目重试。

## 6. 同一话题共同推进任务

### 6.1 新模式任务标识

- 群话题：`agent-topic:<agentId>:<chatId>:<topicId>:service:<version>`。
- 普通群会话：`agent-group:<agentId>:<chatId>:service:<version>`，沿用现有群上下文限制。
- 私聊仍按会话对端隔离；本期不因此向陌生人开放私聊。
- 原有内部 `taskPurpose` 区分继续保留，避免普通协作与内部自动化混用任务。

`agentId` 由受信任的应用配置确定，不从消息传入。新模式保留任务成员和轮次发起人，不再以首位发起人决定谁能提出后续修改。

群服务版本同时固定在任务及其轮次中。撤销后重新启用会创建新版本的共享任务，不复活旧队列、旧确认或旧投递，也不把旧任务版本改成当前版本。

### 6.2 串行推进，避免相互覆盖

复用现有任务锁、活动轮次、follow-up 和消息去重机制，同一任务不因 A、B 同时发言启动两个写入轮次。

- 普通补充进入当前任务的后续输入。
- 如果会改变当前正在执行的操作目标，先停止或完成当前安全步骤，再重新判断，不能静默修改已确认操作的参数。
- 顺序是消息处理顺序，不代表“后一条指令权限更高”。
- 所有者的明确指示优先；普通成员间冲突由代理判断，真正冲突在群内澄清。
- 普通成员可以撤回自己的请求、提出停止建议，但没有停止整个智能体或其他群任务的管理权限。具体任务是否暂停仍按目标与风险判断。

## 7. 执行环境与账号

### 7.1 复用所有者沙箱

第一版继续使用 `UserSandboxManager`，但按 `agentOwnerUserId` 选择所有者沙箱。不再为 A、B 因普通委托分别创建凭据环境。

同一智能体下，各任务保留独立的 App Server 上下文、工作目录和附件范围。继续保留共享项目工作区的写入互斥，防止跨话题同时改写同一目录。

必须审计的不仅是首次创建，还包括恢复、附件导入导出、项目切换、仓库创建、运行时回收和凭据刷新。不能只改 `provision()`，其他路径仍按 A、B 查找沙箱。

共享所有者容器中的不同目录是逻辑隔离，不是强安全隔离。当前模型可执行 shell 时，不能声称不同任务完全无法读取彼此文件。本期不通过改个目录名来制造隔离保证。

### 7.2 工具凭据

- 飞书文档等代表所有者操作的命令显式使用所有者用户身份，不自动降级为 bot 或请求者身份。
- 平台收发消息等应用职责继续使用机器人身份，不把所有 Feishu API 一律改成用户身份。
- 工具凭据留在固定执行环境，沿用 CLI 的原生登录与刷新机制及已有锁。
- 授权完成、凭据变化和恢复时校验实际账号。使用现有 CLI 的身份核验能力，验证账号、凭据有效性和所需 scope。
- 核验结果可以短期缓存，但必须与账号/凭据变化关联；发生身份错误时使缓存失效。
- 身份不符时暂停相关调用，只由所有者修复；不覆盖旧凭据，不向 A、B 发授权请求。
- 授权入口只向所有者提供，授权完成后核验实际登录人。别人误完成授权不能被接受为合法所有者身份。

执行身份和账号校验结果应进入审计，凭据值、device code、授权 URL 中的秘密参数不进入群上下文。

## 8. 自主判断与必要确认

### 8.1 判断所需上下文

任务输入由服务端注入：

- 固定所有者身份与长期规则。
- 真实请求者、可信来源消息、当前群/话题和受众范围。
- 本次任务目标、已执行操作与未完成事项。
- 相关资源来自公开材料、当前群、所有者私人资料还是外部输入。
- 当前群服务版本与有效的所有者确认。

所有者规则与群消息、文档内容、网页内容分开标注。引用、转发和文档中的指令不能晋升为所有者规则。

### 8.2 不建立大而全的规则引擎

一般事项由智能体结合长期规则、任务目标、受众、影响和可撤销性判断：

- 可以做：直接执行。
- 需要补充需求：向提出需求的人或群里澄清。
- 需要所有者授权：只暂停相关操作，找所有者确认。
- 不应该做：说明不能执行，必要时给出可行替代，不先执行再隐藏结果。

不按关键词机械规定“所有创建都审批”“所有内部链接都隐藏”。也不把每一次判断写成新的配置开关。

所有者确认是为有明确必要性的行为提供授权，不是让所有者替代理完成每个日常判断。新增长期规则、扩大凭据权限或替换登录账号仅由所有者决定。

### 8.3 确认与澄清分开

复用现有请求、卡片、过期与幂等能力，但修改处理者语义：

- 普通需求澄清可以由 A、B 回答，不给予所有者授权效力。
- 对所有者权限的操作确认只能由所有者回答，不再取 `activeTurn.createdBy` 作为批准人。
- 确认包含动作、目标资源、必要参数、接收者/分享范围和有效期；参数变化须重新确认。
- 确认绑定任务、群服务版本和操作标识，不能跨群、跨操作复用。
- 不因一个操作等待确认而阻塞整个共享话题。保存暂停动作，先结束该轮的等待，再处理其他安全事项；不要把一个 App Server RPC 永久挂住作为完整调度方案。
- 恢复时重查服务状态、身份和操作条件；重复点击不得重复产生外部写入。

所有者私聊是管理控制通道，不是把被群里隐藏的正文补发给请求者。

### 8.4 可保证的边界

普通自然语言判断由模型完成，不承诺模型不会误判或遭受提示注入。框架强制负责身份、准入、确认处理者、确认范围、撤销与幂等这些可验证事实。

现有 `AppServerRequestService` 只处理 App Server 发出的审批和输入请求，不是所有外部写入的统一拦截器。CLI 的高风险提示也不能被解释为覆盖任意 shell、curl 或脚本的完整防线。

实现时必须验证需要强确认的操作确有执行前阻断路径；不能依靠收到“命令已执行”的事件后再要求确认。对于尚无可信阻断路径的高风险能力，不向群委托开放自动执行，转交所有者受控处理。若要对所有任意命令提供不可绕过的语义授权，需要额外的受控执行层，不伪装成本次小改动已经解决。

## 9. 信息使用、回复与文档交付

### 9.1 可以知道，不意味着可以说

- 默认上下文只载入当前会话相关历史及适合该场景的长期规则。
- 确实需要私人信息时按任务目的读取必要部分，不整包注入私人消息或私人记忆。
- 所有者身份能够访问某资源，不等于群成员有权收到其内容。
- 不直接把 `MemoryActor.userId` 全改成所有者后，向所有群加载其全部私人记忆。
- A、B 的群聊要求不自动变为跨群长期规则；复用已有管理员确认机制。

### 9.2 正文由代理组织，不做默认私聊补发

新模式不再调用 `SensitiveReplyDelivery` 自动保存隐藏行和向请求者私聊交付。

可以说的内容正常说，普通业务链接正常显示；不能说的内容不进入公开消息。无法判断时先澄清或请求所有者决定，不给出一堆占位符后再从其他渠道绕过边界。

不能只设置 `sensitiveReplyDeliveryEnabled=false`：当前类会先脱敏，再检查开关，最终回复还有其他清洗调用。需要区分：

1. **业务披露判断**：由代理结合信息来源、目的和受众完成，不由宽泛正则决定。
2. **认证材料保护**：保留对实际凭据、私钥、认证头等的防泄漏，不将完整业务 URL 因单个参数名就整行删除。
3. **授权控制信息**：仅提供给所有者，不通过群内展示或自动补发给请求者。

历史 `/retry-sensitive` 入口在新模式下不继续补发旧记录，明确说明不可用；凭据材料不迁移进新回复通道。历史存储保持原有过期处理，不在迁移时批量删除旧目录。

### 9.3 所有输出通道使用同一受众边界

必须覆盖最终答复、流式进度、卡片预览、折叠详情、附件、导出文件、直接 CLI 发消息与文档分享。

- 公开执行进展由代理主动组织，不能无条件同步原始 stdout、私人资料正文或所有者确认内容。
- 原始诊断记录与公开执行过程区分，沿用现有详情来源和访问核验；折叠不是权限隔离。
- 针对已明确需要所有者决策的动作，等待摘要本身也不得提前披露待决策的秘密。
- 公开文本、附件和链接目标的访问范围必须一致。不能正文拒绝披露，却附上包含同样内容的文件。

### 9.4 为群新建文档

在本方案长期授权下，普通创作按以下步骤完成：

1. 判断请求与内容适合当前群。
2. 用所有者用户身份创建文档，归属遵循飞书实际空间规则。
3. 针对本次为该群新创作的文档，赋予当前群可阅读的访问范围，不默认开放编辑或匿名公开。
4. 核验分享操作及实际阅读权限，再在群内交付链接。

实现时使用现有文档、云盘 CLI/技能；先验证平台是否支持目标类型的群阅读权限。若无法表达或验证群级阅读，不自动退化为“任何拿到链接的人可读”，也不把所有者自己能打开当成交付成功，应说明具体限制并寻求合适处理。

这项默认授权不扩展到所有者既有私人文档、被引用资料或私人目录。为群新建的文档如果包含不适合群的内容，应先改写或暂停披露，而不是先分享后解释。

## 11. 迁移与回退

### 11.1 迁移顺序

1. 新配置、新字段、新模式独立启用，默认不扩大当前线上准入。
2. 先以所有者请求验证固定身份、账号核验和现有工作流兼容性。
3. 对一个由所有者明确授权的群试运行，验证真实邀请事件、A/B 协作、文档交付和退出停止。
4. 验收通过后再扩大启用范围，不把所有历史所在群自动当成所有者邀请。

### 11.2 历史处理

- 旧的按用户划分任务保留原始标识和归属，不批量修改成新所有者。
- 同一群话题中已有 A、B 两个旧任务时，新建共享任务；只从该话题可验证的共同材料中恢复必要背景，不直接合并两人的私有上下文、文件或凭据。
- 当前运行中的旧任务先安全收尾或停止，新模式不能与旧任务同时执行同一业务写入。
- 其他用户的凭据不复制到所有者沙箱；原用户 Docker 卷、CodeBot 目录和迁移备份不自动删除。
- 旧待授权、待确认及敏感补发记录不能因为启用新模式就获得新执行权限。

### 11.3 回退

关闭个人代理模式时，先关闭已开放群的委托入口，撤销新模式待确认和待执行操作，再受控恢复只允许所有者使用的安全基线。

不能只切回旧路由、同时保留群成员的开放准入，否则可能重新使用请求者凭据和旧授权语义。

回退保留文档、会话、审计和业务结果，不自动删除外部产物，也不直接恢复旧数据库覆盖新数据。只有实际数据库迁移或批量改写才执行相应备份和迁移验证，不让普通配置或代码修复都做全库扫描。

## 12. 验收标准

| 场景 | 预期结果 |
| --- | --- |
| 所有者可信邀请进群 | 群服务启用，成员可提出普通任务；不需要逐人加入白名单。 |
| 非所有者邀请，或邀请人不可核验 | 不自动启用，等待所有者确认。 |
| A 创建文档，B 在同一话题补充 | 同一任务、同一文档继续推进；审计能区分两人的要求。 |
| A、B 同时发送修改 | 同一任务串行处理，不产生互相覆盖的两个写入轮次。 |
| A/B 请求普通文档创作 | 使用所有者身份，不要求 A/B 授权。 |
| A/B 完成了错误账号授权 | 实际账号核验失败，相关操作不执行。 |
| 所有者凭据失效或 scope 不足 | 仅向所有者请求修复或增量授权，不回退到 A/B 或 bot 身份。 |
| 所有者与群成员指示冲突 | 所有者明确指示优先，真实身份来自平台而非正文。 |
| 两位群成员要求冲突 | 代理判断或在群内澄清，不默认首位/最后发言者有最终权力。 |
| A/B 要读取所有者相关资料 | 按需判断，私人历史不整包载入；披露范围独立判断。 |
| 群任务尝试直接加载全部私人记忆 | 被上下文选择边界阻止，不因共用身份而放开。 |
| 待所有者确认 | 仅相关操作暂停，群里其他安全工作继续；A/B 不能批准。 |
| 确认后修改目标或分享范围 | 原确认不能复用，必要时重新确认。 |
| 为群新建文档 | 所有者身份创建、群内可读、不默认可编辑、无匿名公开。 |
| 分享不受平台支持或核验失败 | 不伪报交付成功，不自动扩大为公开链接。 |
| 普通业务链接包含 `ticket`/`state` 等参数 | 不因宽泛正则整行消失，链接保持可用。 |
| 凭据或私钥进入工具输出 | 不出现在公开进度、折叠详情、附件或日志公开出口。 |
| 新模式触发旧敏感补发入口 | 不向 A/B 发送隐藏内容，不复用历史补发权限。 |
| 所有者停止服务，或机器人被移出群 | 新请求、轮次、跟进、待确认和未投递结果停止；旧邀请事件重放不能重新启用。 |
| 服务撤销后重启，或重新邀请后点旧卡 | 不恢复旧队列、不执行旧确认；已提交外部操作先核实结果。 |
| 普通群成员使用维护/授权管理入口 | 被拒绝，群任务准入不等于管理员权限。 |
| 不同群和话题 | 不共享私人上下文、不串发附件和确认结果。 |
| 迁移或回退 | 不删除原 CodeBot、Docker 卷及迁移备份，不覆盖新业务数据，不误用其他用户身份。 |

## 13. 实现前必须确认的技术事项

产品行为不再重新询问。以下项目由实现阶段通过源码、CLI 和受控环境验证：

1. 飞书邀请、移除事件的实际字段及事件订阅权限，是否能够可信识别所有者邀请。
2. 当前 CLI 对目标类型文档的群阅读权限支持与读后核验能力。
3. CLI 用户身份校验、凭据变化检测和同一所有者并发刷新行为。
4. 所有者确认在任意命令执行前的实际阻断范围，以及暂不能开放的高风险能力。
5. 等待所有者决策时，共享任务能继续接受其他安全请求的恢复机制。
6. 所有公开输出路径与旧模式恢复路径的完整清单。

以上任一能力未验证，必须在验收结果中明确列为未完成，不能用“模型会自行判断”代替工程事实。

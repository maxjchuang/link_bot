## 1. 实施原则与完成标准

黄小成以所有者的身份代理办事。真实请求者继续记录，群成员不会因此获得所有者的管理权限。

本次不开发通用权限引擎，不重写飞书或其他内部平台客户端，不替换容器管理框架，不顺带重做卡片 UI。复用已有任务、沙箱、CLI、确认请求、outbox、记忆和状态存储。

本计划的最终完成标准不是“字段已经加上”或“测试全部通过”，而是受控真实验收证明：

1. 所有者启用的群中，A 发起、B 补充，始终使用同一个话题任务和所有者执行身份。
2. 普通任务不要求 A、B 授权；确需确认或修复凭据时只找所有者。
3. 等待所有者决策不会长期占住整个共享话题；其他安全请求能继续推进。
4. 为群新建的文档使用所有者身份，群内可读；既有私人资源不会被顺带共享。
5. 普通业务链接不再被宽泛规则隐藏；凭据不进入公开消息、卡片、附件或详情。
6. 撤销服务、重启恢复、旧卡片和旧消息重放都不能重新获得执行资格。
7. 关闭个人代理模式后回到只允许所有者使用的安全基线，不恢复请求者凭据语义或旧待执行授权。

任一项没有证据，就记录为未完成。不得以“模型应该会判断”代替程序校验，也不得把同一容器中的目录划分描述成强安全隔离。

2026-11-21 执行调整：所有者已明确将真实群事件、成员创建文档等验证移到整体交付后统一进行。下文关于真实验证的开发前置门槛据此解除；程序侧身份、快照、版本围栏和失败关闭要求不变。尚未执行的真实场景继续标为待验收，不填写为通过。

## 2. 开工规则与代码组织

### 2.1 本计划与本地执行材料

本文件是应提交的正式实施计划，不放入 `docs/superpowers/plans/`。该目录只允许存放被忽略的本地执行材料，不得强行加入 Git。

后续提交文档时，设计稿与本计划必须一起提交。实际仓库地址、用户 ID、群 ID、登录状态、凭据、私有规则、运行日志和验收原始记录保存在被忽略的本地状态目录，不写入这两份文档或测试。

### 2.2 执行与提交方式

- 每个工作包先补失败测试，再实现最小改动，最后做针对性回归。
- 以工作包为建议提交边界，避免将身份、群开放和回复改造混成一个大提交。
- 新模块名和接口在下文中标注“拟新增”；现有模块直接复用，不因命名建议重复创建同类服务。
- 新功能全程受 `personalAgent.enabled` 控制，开发和部署初期保持关闭。群服务记录为启用状态不等于总开关已经开放。
- 不全局替换 `userId`，不把群成员伪装成管理员，不将沙箱执行身份作为内存读取与公开交付的授权捷径。
- 普通代码修改不扫描或备份整个生产数据库。确有 schema 迁移时，才按该迁移准备一致性备份和恢复验证；诊断查询使用只读连接。
- 不自动删除 CodeBot、原 Docker 卷、迁移备份或旧敏感补发目录。

## 3. 固定的数据契约

### 3.1 身份契约

拟新增一个集中解析入口，例如 `src/security/AgentExecutionIdentity.ts`：

```ts
interface AgentExecutionIdentity {
  mode: 'legacy' | 'personal-agent';
  agentId: string;
  agentOwnerUserId: string;
  requesterUserId: string;
  audience: {
    chatId: string;
    chatType: 'private' | 'group';
    topicId?: string;
  };
  groupServiceVersion?: number;
}
```

- `agentId` 从可信应用配置派生，不接受消息正文或卡片参数指定。
- 个人代理模式的执行所有者来自服务端配置，并与任务中固定的所有者一致。
- 请求者来自已认证消息、回调或持久化轮次，不接受正文中的身份自述。
- 受众来自任务 scope 和实际投递目标，不能因向所有者申请确认就改成私人任务。
- 缺少必要身份、模式不明或任务与配置所有者冲突时，停止相关调用；不能退回请求者或机器人账号执行。

兼容写入明确如下：历史任务不改 `ownerUserId`；新模式任务的 `ownerUserId` 写固定所有者作为兼容归属字段，同时持久化 `agentOwnerUserId` 和模式标记。真实发起人保留在 `TurnRecord.createdBy`、请求记录及审计中。A 创建共享任务时不是任务管理上的 owner，不能取得所有者权限。

### 3.2 群服务与待确认契约

群服务只增加必要状态：智能体、群、所有者、启用或撤销状态、单调递增版本、可信事件标识和最近应用时间。使用现有 SQLite 迁移机制；实现时再分配版本号，不在计划中预占。

轮次、待确认操作、接续、定时跟进和待投递结果必须能关联原群服务版本。版本绑定的是本次操作获准进入系统时的资格，不能在重试时悄悄换成当前版本。

确认请求继续复用现有 request ID、generation、有效期和去重能力，补充确认目的、真实请求者、执行所有者、来源 scope、群服务版本和服务端生成的操作快照摘要。不要复制一套审批数据库。

## 5. 工作包与验收

### P0：先验证事实，不先堆实现

**核对位置**：`src/feishu/FeishuGateway.ts`、`src/approvals/AppServerRequestService.ts`、`src/tasks/TaskPlatformService.ts`、`runtime/bin/lark-cli-wrapper`，以及现有 CLI 的帮助和实际输出。

需要产出六项结论：

1. 邀请和移除事件的订阅权限、操作人字段、事件 ID、时序和重复投递表现。无法识别邀请人的事件只能进入待所有者确认，不能推测为所有者邀请。
2. CLI 如何区分 bot 与 user、查询实际账号、检查 scope、恢复授权；登录、核验和执行必须使用同一受控 UID、HOME 和持久化凭据路径。核对 `open_id`、`user_id`、`union_id` 的应用命名空间：不同应用的 `open_id` 不能直接比较，须使用可信映射或可核验的共同标识；昵称相同不是身份凭证。
3. 目标文档类型是否支持当前群可读、不可默认编辑，以及如何以非所有者身份验证阅读权限。
4. 当前 App Server 确认请求挂起时，任务输入、任务锁和 follow-up 实际如何阻塞。
5. 能否在不执行待确认操作的前提下释放主话题轮次，并通过持久化待办在后续轮次恢复。
6. shell、动态工具、CLI 直发、卡片和附件分别有哪些控制入口，哪些暂时无法程序化拦截。

**验证方法**：先用现有测试和假后端复现；涉及平台写入时使用所有者明确同意的测试群与最小测试资源。记录工具版本、命令、返回字段和结果，不把登录成功、API 查询成功当成业务操作成功。

**产物**：公开结论补入实施记录；具体地址、账号、授权链接和原始输出只在本地保留。邀请人识别、群阅读或非阻塞恢复无法验证时，标记阻塞对应工作包，不用临时放宽权限替代。

### P1：配置、身份解析与兼容字段

**修改**：`src/config/loadConfig.ts`、`src/domain/types.ts`、`src/tasks/TaskTypes.ts`、集中身份解析模块；配置示例只使用占位值。

步骤：

1. 增加 `personalAgent.enabled` 和 `ownerUserId`，默认关闭；开启时校验所有者存在、沙箱路径可用、管理员和宿主管理身份不存在冲突。
2. 任务 payload 增加模式与固定所有者字段，读取旧记录时保持旧模式。禁止仅凭当前总开关把所有历史任务解释成新模式。
3. 实现并集中使用身份解析入口，普通群请求者没有写入执行所有者字段的入口。
4. 列出全部 `ownerUserId`、`actor.userId` 使用点，区分“实际发言人”“执行归属”“管理权限”“交付受众”。后续工作包按这份清单逐项关闭，不凭搜索替换完成改造。

**测试**：扩展 `tests/config/loadConfig.test.ts`；新增身份解析测试，覆盖旧记录、A/B 请求、缺字段、配置所有者变化、伪造正文与卡片参数。证明真实请求者始终保留，新模式不存在请求者身份回退。

**退出条件**：模型契约稳定，总开关关闭时原有路由与任务读取行为不变。

### P2：群服务状态、可信邀请与撤销记录

**修改**：`src/state/SqliteSchema.ts`、`SqliteStateStore.ts`、`src/feishu/FeishuGateway.ts`；拟新增最小群服务模块与测试。

步骤：

1. 增加群服务记录和按事件去重、版本更新的事务方法；重复事件不能重复增加版本，旧启用事件不能覆盖新撤销。
2. Gateway 将已验证事件规范化后交给群服务模块，不把原始事件正文作为可信授权依据。
3. 增加一种最小的所有者显式管理入口：拟使用所有者私聊中的 `/agent group enable <chat_id>` 与 `/agent group disable <chat_id>`。它们是拟新增命令，不是当前已支持功能；不另做管理后台。
4. 显式启用前确认目标群确有机器人且所有者具有确认资格；启用过程不修改全局 `allowedUsers`，也不打开 `allowUnlistedGroupUsers`。
5. 成员身份查询失败时不采用过期的允许结果。仅有成员进入或退出事件不能当作所有者邀请授权。

**测试**：扩展 Gateway 测试；新增群状态测试，覆盖可信/不可信邀请、显式确认、重复和乱序事件、移除、停止、重新邀请、数据库重开后的版本保留。

**退出条件**：只具备资格记录与撤销事实，生产群成员仍未被放行。

### P3：共享话题任务，不共享管理身份

**修改**：`ConversationTaskService.ts`、`TaskTypes.ts`、`SqliteStateStore.ts`、`src/feishu/FeishuTaskController.ts`。

步骤：

1. 新模式使用设计稿的 `agent-topic`/`agent-group` scope key，保留 `taskPurpose`；私聊不因新模式开放给陌生人。
2. 任务新建时写固定所有者；A、B 作为实际参与者记录，不把最初发起人设为新模式的管理 owner。所有者的资格来自配置，不来自谁先发言。
3. 复用 scope 锁、任务锁、去重和 follow-up，保证 A、B 并发输入只创建一个规范任务、不产生并发写入轮次。
4. 新模式解析不能调用会误认旧个人任务的兼容回退；发现旧个人 scope 时按 P9 处理，不直接并入新共享上下文。
5. 调整普通请求与管理动作的区分，成员能补充需求，不代表能删除任务历史、管理成员、修改长期规则或维护宿主。

**测试**：扩展 `tests/tasks/ConversationTaskService.test.ts` 与 controller 测试；A 建任务、B 解析为同一任务，A/B 发言分别记录；不同群、话题、purpose 不串任务；并发创建和重复消息只产生一项任务及一次执行。

### P4：执行环境与工具账号固定到所有者

**修改**：`UserSandboxTaskProvisioner.ts`、`UserSandboxManager.ts`、`UserSandboxReclaimer.ts`、`UserSandboxAppServerRuntime.ts`、`src/app/createTaskPlatform.ts`、项目创建/绑定调用点、`runtime/bin/lark-cli-wrapper`。

步骤：

1. 将沙箱创建、恢复、recycle、附件暂存/导出、仓库创建、项目绑定与切换、认证刷新、资源回收全部接到固定执行所有者解析。实际请求者和来源 scope 单独传递，不伪造整个 actor。
2. A、B 进入同一所有者容器，但保持独立任务上下文、任务附件范围和现有共享项目写锁。沿用容量与 lease/generation 围栏。
3. 复用 CLI 原生凭据存储和刷新锁，核对实际 user 账号与所有者一致；平台收发消息继续使用 bot 身份。
4. 登录、查询账号和业务执行使用相同 UID/HOME/凭据路径；不得出现 root 下登录成功、任务 UID 读取不到登录态却仍宣布就绪。
5. 身份核验缓存关联账号和凭据变化；错误账号、凭据失效或 scope 不足时只通知所有者，不覆盖旧凭据，也不向 A/B 请求授权。
6. 项目访问判断拆成代理自身的资源资格与当前群请求范围，不将请求者替换为管理员去调用全部旧权限逻辑。

**测试**：扩展现有 runtime、App Server 和 project policy 测试。覆盖所有入口上的 A/B→同一所有者沙箱、旧任务原归属、身份不符、无 user 身份时不降级 bot、并发刷新、重启恢复和跨话题附件隔离。加入执行 UID/HOME 与身份核验一致、跨应用身份可靠映射以及不同账号同名不能通过的回归测试。

**退出条件**：所有者相关调用点清单无遗漏；只验证“账号是谁”不足以通过，至少一项受控业务操作须成功。

### P5：任务上下文、记忆与一般行动判断

**修改**：`TaskPlatformService.ts`、现有上下文构建模块、`src/memory/MemoryService.ts`、记忆投影、`ProjectAccessPolicy.ts`、运行时默认指令。

步骤：

1. 服务端向任务注入所有者、请求者、受众、群服务版本和相关长期规则；群消息、引用与外部文档明确标为任务材料，不能提升为系统授权。
2. 默认只加载该话题必要背景，不将私人记忆 actor 统一改成所有者后全量 recall。允许按需读取相关私人资料，但来源范围和披露判断分开。
3. 记忆写入保留实际提出者；跨群长期规则仍走所有者控制，不因成员在群中说“以后都这样”自动生效。
4. 使用简短稳定的行为准则指导一般事项判断，不为每类业务增加配置开关，不以关键词决定所有创建都审批或所有内部链接都隐藏。
5. 长期规则变更、维护、授权管理、扩大凭据权限仍由程序限定到所有者；群服务资格不改变这些硬边界。

**测试**：扩展 MemoryService、MemoryProjectionService、上下文和任务平台测试。群任务默认看不到完整私人历史；按需资源有来源标识；A/B 不能直接确认长期记忆；所有者明确指示与普通补充可区分；引用中的身份自述不改变执行身份。

**退出条件**：不能仅给所有者权限后指望 prompt 防住全部上下文泄漏，默认注入与受控读取边界需有程序测试。

### P6：确认找所有者，澄清找请求者；主话题能继续

**修改**：`AppServerRequestService.ts`、`AppServerRequestTypes.ts`、对应存储方法、确认卡片、`TaskPlatformService.ts` 和现有任务恢复机制。

步骤：

1. 在现有请求中增加明确的“需求澄清/所有者授权”目的。授权请求处理者为固定所有者；普通需求澄清保留真实请求者。`kind=user_input` 本身不能证明它只是澄清。
2. 确认记录绑定服务端生成的操作快照、来源任务/轮次、连接 generation、群服务版本和有效期。回调重新验证平台身份，不能信任按钮传来的 owner。
3. 所有者确认卡私聊交付，群内只显示不泄漏待确认内容的状态；发送失败不执行。A/B 点击确认、转发旧卡或修改参数均不能放行。
4. 将业务上的待决策事项持久化为“等待所有者的操作”，而不是无限保留共享话题的 `activeTurnId`。主轮次在确认该操作未提交后安全结束，后续安全输入继续按现有队列推进。
5. 以 P0 原型验证上一步的具体接法。若已有 App Server 原生请求挂起，不能把它的 request ID 搬到另一连接：只能在协议允许且确定未执行时安全拒绝或取消本次调用，再持久化可恢复事项。不能靠手动清空 `activeTurnId` 释放任务。
6. 所有者确认后，通过已有接续机制进入新轮次，重新核对原操作参数、账号、群版本和外部结果。只对受控、可验证的操作执行恢复；不盲目重跑整个旧轮次或任意旧 shell 文本。
7. 将“澄清需求”和“扩大授权”区分，不能把普通成员的澄清答复当成所有者批准。

**必须通过的测试**：A 的操作等待确认时，B 的独立安全请求能够完成；A/B 不可批准；所有者批准后只恢复相关操作一次；参数变更、超时、群撤销、连接重建和重启后的旧确认均不能误执行；外部结果未知时先查询，不重复提交。

**硬门槛**：如果原型无法证明安全结束主轮次与精确恢复，P6 不算完成、群准入不开启。任意 shell 的控制覆盖需如实列出，不能把业务待办机制包装成已经硬拦截所有外部写入。

### P7：统一公开输出与文档交付

**修改**：`SensitiveReplyDelivery.ts`、`DetailSanitizer.ts`、`InlineTurnDetails.ts`、卡片/结果/附件发布模块、`src/index.ts`、`src/app/createTaskPlatform.ts`、`src/host-manager.ts` 和现有 CLI 调用封装。

步骤：

1. 新模式跳过旧的隐藏行保存与向请求者私聊补发链路；旧模式保留兼容实现。旧 `/retry-sensitive` 记录不能在新模式恢复投递。
2. 将业务正文处理与凭据保护分开。对真实令牌、私钥和认证头继续拒绝泄漏，普通业务 URL 不因含 `ticket`、`state` 等字段被整行删除；真正的认证链接仍仅供所有者。
3. 逐项登记最终答复、流式进度、卡片预览、折叠详情、最终结果恢复、附件、导出、CLI 直发和文档分享入口，全部使用同一受众语义。
4. 不将任意原始 stdout 自动认定为公开过程。原始诊断仍受现有详情授权约束；凭据保护需覆盖其存储和公开出口，不能只处理最后一段答复。
5. 通过现有文档和云盘 CLI，以所有者 user 身份为群创作、设置群可读、核验非所有者阅读，再交付链接。不匿名公开、不默认编辑、不修改既有私人文档权限。
6. 文档创建成功但分享失败时记录部分成功与外部资源标识；重试只修复失败步骤，不重复创建，不伪报“已交付”。

**测试**：扩展 SensitiveReplyDelivery、DetailSanitizer、InlineTurnDetails、卡片和结果恢复测试；增加所有输出入口的表驱动用例。分别证明业务链接保留、真实凭据不公开、A/B 不收到隐藏内容、旧补发入口失效、附件与正文边界一致。文档假后端验证 owner 身份与群只读参数，真实群阅读留到 P9 验收。

**退出条件**：发布入口清单完整；仅关掉私聊开关、让其他 sanitizer 继续粗暴删正文，不算完成。


### P8：统一入口准入与撤销围栏

**修改**：`src/index.ts`、`src/security/guards.ts`、Gateway 和 task controller、`TaskPlatformService.ts`、outbox、详情访问控制、确认回调和恢复任务；接入 P2 的群服务记录。

步骤：

1. 消息、卡片和详情读取共用准入入口，结合真实操作人、当前群成员资格、来源消息、任务 scope 和群服务状态核验。只拿到 task ID、旧卡片、转发消息或附件链接不能取得访问或操作资格。
2. 新模式普通群任务的放行条件为：总开关开启、该群服务启用、实际请求者是当前成员、操作属于普通任务入口。宿主管理、运行时升级、授权管理和长期规则入口仍仅所有者可用。
3. 不修改全局用户白名单来模拟群准入，不对所有群开放。不顺带改变当前 mention、话题和 ambient conversation 策略；这些策略与群服务资格同时生效。
4. 轮次、待确认事项、恢复任务、定时跟进和 outbox 保存提交时的群服务版本。至少在开始轮次、接受所有者确认、受控外部动作提交前，以及每次投递/重试前核对当前版本；拒绝已撤销或版本不符的工作。
5. 撤销时先事务性持久化新版本和停止决定，再取消队列、确认与重试，并中断活动轮次。不能只停当前进程或只改变内存里的标记；重启后仍以持久化状态为准。
6. 不跨网络持有数据库事务。外部提交保留意图、幂等标识和回执；区分撤销发生在提交前、提交中、提交后三种结果。提交中的动作只能尽力取消，结果未知的先核实，不能伪报撤回成功。
7. 旧 outbox 不因已排队就自动发送；服务重新启用后也不改写旧任务版本来恢复执行。重新邀请只允许产生新工作。
8. 校验消息/成员资格的 API 不可用时停止相关入口，明确记录失败，不退回“群曾经启用过，所以继续允许”。

**测试**：新增准入与撤销集成测试，扩展 `tests/security/guards.test.ts`、Gateway、controller、`tests/feishu/FeishuOutbox.test.ts` 和详情测试。覆盖未授权群、退群成员、转发卡片、旧确认、乱序邀请、排队后撤销、发送失败重试、定时跟进、断线重启及重新邀请。用可控后端模拟撤销与外部提交的竞态，验证不会重复操作或虚报已撤销。

**退出条件**：没有“消息被拒绝、卡片仍放行”或“新任务被停止、旧队列仍执行”的旁路。只有到这里才允许在所有者确认的单个测试群开放真实成员请求。

### P9：迁移、完整验收与回退

**修改**：模式选择、旧任务交接、部署检查和回退步骤；仅对必要的 schema 变更执行数据库迁移。

步骤：

1. 旧个人任务保留原模式、请求者和凭据归属。新模式新建共享任务，不批量改写旧记录，不把 A/B 私有历史与工作区合并进所有者任务。
2. 同一业务写入的新旧任务不能同时执行；交接前安全收尾或停止，之后只恢复该话题可验证的共同材料。
3. 旧待授权、待确认、敏感补发和不明确状态的操作保持隔离；新模式不开启它们的执行资格。
4. 总开关关闭时先阻止新的群委托，再撤销新模式待确认/待执行和待投递操作。已标记的新模式任务不能因为关开关就被当成 legacy 任务执行。
5. 回退目标是只允许所有者使用。它不恢复群成员的旧请求者授权，也不通过旧数据库覆盖新文档、会话或审计。
6. 数据库 schema 回退与功能开关回退分开。旧二进制不支持新 schema 时，不直接降级启动；先采用兼容新 schema 的关闭新模式版本，并验证实际部署路径。

**测试**：旧 payload 读写、schema 升级和幂等重启、跨模式查询、owner 配置不一致、关闭后旧卡回调、执行中回退、模式反复切换、原卷与历史资料保留。实际 schema 迁移需在一致性副本上演练，不在生产全库上反复试改。

## 6. 测试、审查与真实验收

### 6.1 每个工作包的验证记录

每包记录修改文件、测试场景、运行命令、退出码、失败原因和未完成项。测试以虚构 owner/A/B、群 ID、账号和仓库地址构造，不能把生产凭据或日志改名后塞进 fixture。

示例验证命令如下；新增测试文件名按实际落地同步更新：

```sh
npx vitest run tests/config/loadConfig.test.ts tests/tasks/ConversationTaskService.test.ts
npx vitest run tests/runtime/UserSandboxTaskProvisioner.test.ts tests/runtime/UserSandboxManager.test.ts
npx vitest run tests/approvals/AppServerRequestService.test.ts
npx vitest run tests/memory/MemoryService.test.ts tests/memory/MemoryProjectionService.test.ts
npx vitest run tests/details/SensitiveReplyDelivery.test.ts tests/details/InlineTurnDetails.test.ts
npx tsc --noEmit

```

上面不是新增场景的完整清单，不能以这些旧测试通过代替各工作包要求的新测试。最终还要构建候选运行镜像，验证镜像内实际 CLI、任务 UID、凭据路径与代码一致；仅宿主单测通过不代表沙箱可用。

### 6.2 对抗审查清单

- 是否仍有某条恢复/附件/仓库路径按请求者选择沙箱？
- 是否只是给 A/B 换了 owner ID，结果连管理员、记忆或确认权限也一并换了？
- 是否把“API 可查询”“所有者可打开”“消息 API 返回成功”当作完整业务交付？
- 是否有 shell/CLI 直发、附件或折叠详情绕过正文边界？
- 所有者确认是否绑定实际参数，是否存在清空 active turn 或跨连接重放请求的捷径？
- 撤销是否只能阻止新消息，却拦不住 outbox、跟进、旧卡和重新启动？
- 是否为解决一个内部平台问题改造 LinkBot 框架，或向公开源码写入本地仓库配置？
- GitHub 提交与 PR 发布是否仍经过现有身份和敏感内容强校验？个人代理模式不能关闭或绕过它。

### 6.3 必须保留的真实验收证据

| 验收组 | 真实操作 | 必须观察到的证据 |
| --- | --- | --- |
| 身份与协作 | 所有者启用测试群，A 建文档，B 补充 | 一个话题任务、两位真实请求者、同一所有者执行账号；A/B 未授权 |
| 文档交付 | A/B 打开新文档，尝试编辑；再请求引用旧私人文档 | 新文档群可读、未默认编辑；旧私人资源未被自动共享 |
| 等待与继续 | A 的一项操作等待所有者，B 发独立安全请求 | B 能继续；A/B 的确认无效；所有者确认只恢复原操作一次 |
| 公开边界 | 普通链接、凭据样本、工具输出、附件和详情 | 业务链接可用；凭据无公开落点；不向 A/B 自动私聊补发 |
| 撤销与恢复 | 所有者停止、移出机器人、重启、重新邀请、点击旧卡 | 旧任务、确认、跟进和待发结果不复活；已提交操作先核实结果 |
| 迁移与回退 | 留存旧个人任务，开启后再关闭新模式 | 旧私有材料不合并；只恢复所有者入口；业务结果、原卷和备份保留 |

真实场景需要可区分的所有者、A、B 测试身份。若当前环境仅允许所有者且无法提供参与者，单元测试可先完成，但多人真实验收必须标为待完成，不能用同一个账号代替三种身份后宣告通过。

验收原始证据只保留在本地；公开文档记录步骤、结果、版本与未完成项，不记录真实账号、群、仓库地址或凭据。

## 7. 发布与回退顺序

1. 确认工作包和审查通过，设计稿、计划与实现一致；生产配置仍保持新模式关闭。
2. 检查拟提交文件及暂存 diff，排除本地状态、凭据、执行材料和其他无关修改。设计稿与本计划一起进入正式文档提交；实现按工作包分别提交。
3. 使用已获准的个人 Git 身份和现有发布强校验。被拒绝时检查内容或身份，不绕过 hooks、不强制加入忽略目录。
4. 部署兼容版本、验证 schema 与实际进程；需要容器侧变化时构建并验证候选镜像，不能只重启网关就声称 wrapper 生效。
5. 按现有安全重启机制切换。活跃任务先安全收尾；Host Manager 自身重启仍延迟到当前轮次及卡片完成后，不直接杀死正在部署的维护轮次。
6. 总开关开启后只启用受控测试群，执行完整真实验收。未通过时立即关闭群委托入口并按 P9 撤销新模式操作，再回到只允许所有者的安全基线。
7. 全部验收通过后逐群启用。记录运行提交、镜像、schema、配置状态和验收结论，不在回复结束前把“已安排重启”写成“重启后检查通过”。

回退保留兼容二进制、旧镜像和本地配置快照。不得自动恢复旧数据库覆盖新业务数据，也不得为了回退删除原 CodeBot、持久卷或外部文档。
